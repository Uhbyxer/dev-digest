# onion-architecture — eval

Три незалежні кейси. Кожен — окрема папка в `fixtures/`, у якій немає жодних
коментарів-підказок. Еталон (де порушення і яке правило) лежить окремо в
`expected-findings.json` — агентові під час прогону його не показувати.

## Task prompts

Підставляти шлях до фікстури замість `<fixture>` (відносно цієї папки).

**1 · `reviewer-core-imports`**
> Я готую PR у dev-digest. Файли з reviewer-core лежать у `<fixture>`. Перевір їх на архітектурну чистоту для цього репо: для кожної проблеми дай file:line, що саме не так і як виправити. Якщо файл у порядку — так і скажи.

**2 · `server-seams`**
> Я готую PR у dev-digest. Модуль notes (бекенд, server/) лежить у `<fixture>`. Перевір його на архітектурну чистоту для цього репо: для кожної проблеми дай file:line, що саме не так і як виправити. Якщо файл у порядку — так і скажи.

**3 · `mixed-pr`**
> Я готую PR у dev-digest, він зачіпає і reviewer-core, і server/. Змінені файли лежать у `<fixture>`. Зроби архітектурний рев'ю для цього репо: для кожної проблеми дай file:line, що не так і як виправити. Не вигадуй проблем там, де їх нема.

Промпти не згадують onion/hexagonal — скіл має спрацювати за описом.

## Scoring

Порівняти знахідки агента з `expected-findings.json`:

- **Recall** = (очікувані знахідки, що збіглися за file+line) / (усі очікувані знахідки, тут 9).
  Збіг = той самий файл, рядок у межах ~3 від еталонного і згадка всіх `must_mention`.
- **Precision** = (збіглі знахідки) / (усі знахідки, подані як порушення архітектури).
  Зауваження не про шарування (друкарські помилки, нейминг, N+1, `JSON.parse` без try/catch
  та інші code smells) на precision не впливають — рахується лише те, що подано *саме як*
  порушення onion-архітектури. Файли з `must_not_flag`, названі порушенням, — це
  хибні спрацьовування і знижують precision.
- **Pass threshold**: `recall >= 0.85`, тобто з 9 знахідок можна пропустити щонайбільше одну
  (8/9 = 0.89 проходить, 7/9 = 0.78 ні), **і** жодного файлу з `must_not_flag` у порушеннях.

Додатково (якісно, не входить у поріг):

| Перевірка | Правило |
|---|---|
| Напрям виправлення | інфраструктуру виносять назовні (adapter / repository / container / інжектований клієнт), а не «додати в core» |
| Без вигадок | жодних пропозицій `domain/` у `server/` чи розбиття `reviewer-core` на під-шари |

## Як запускати вручну

Для кожного кейсу — два субагенти з тим самим промптом: один зі скілом, один
без (baseline без Skill-тула і без читання `.claude/`, `docs/`). Порівняти
recall і хибні спрацювання. Скіл має давати результат не гірший за baseline —
різниця є лише на складніших фікстурах, ніж ці (див. `skill-evals/_shared/README.md`).
